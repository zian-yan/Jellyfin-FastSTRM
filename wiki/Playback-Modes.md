# 播放模式：有流与无流

FastSTRM 的分流判据只有一个：条目在数据库里是否已有流信息，即 `RunTimeTicks > 0`。由此产生两条完全不同的播放路径。

| 类型 | 判定条件 | 库中状态 |
| :--- | :--- | :--- |
| **有流 `.strm`** | `RunTimeTicks > 0` | 已探测过，时长、码率、音视频与字幕轨（`MediaStreams`）均已入库 |
| **无流 `.strm`** | `RunTimeTicks` 为空或 `0` | 新入库未扫描、预探测未覆盖，或上次探测失败 / 超时 |

> 时长未知的极端条目（如部分直播型 `.strm`）即使探测成功也会被判为无流，属预期行为。

---

## 播放决策流程

```
PlaybackInfo 请求
    │
    ├── 非 .strm ─────────────────────────────────▶ 原生透传
    │
    └── .strm
         ├── 有流 ──▶ allowMediaProbe = false ──▶ 秒开（无条件，不受任何配置影响）
         │
         └── 无流
              ├── 跳过探测 = 开（默认）
              │     ├── 起播后策略 = 不补探测（默认）──▶ 秒开，不再请求流地址
              │     └── 起播后策略 = 后台补探测 ──────▶ 秒开 + N 秒后补探测
              └── 跳过探测 = 关 ────────────────────▶ 官方 ffprobe（首次等待，成功后转为有流）
```

分流发生在 `MediaSourceInterceptor.GetPlaybackMediaSources`；`allowMediaProbe = false` 即阻止 Jellyfin 对远程地址发起探测，客户端拿到媒体源后直接直连播放。

---

## 一、有流 `.strm`

**触发条件**：条目已有 `RunTimeTicks > 0`。典型来源是运行过增量/全量预探测、命中入库自动探测，或曾在官方探测模式下完整探测成功过一次。

**行为**：`allowMediaProbe` 被强制置为 `false`，直接复用库中已有的 `MediaStreams` 起播；不调度任何补探测，不再访问流地址。

**特点**

- 起播毫秒级，且**始终如此** —— 该路径不读取任何配置项。
- 时长、码率、音轨、字幕轨完整，进度条与续播、看完判定、轨道切换均由 Jellyfin 原生逻辑处理。
- 代价：信息来自数据库缓存，源端内容变更（换片、改码率）不会自动反映，需手动跑一次**全量探测**刷新。

**适用场景**：已完成预探测的媒体库；对体验要求最高的主力库；客户端对缺失流信息兼容性差（TV 端、部分第三方 App）。

---

## 二、无流 `.strm`

无流条目由配置项 `SkipProbeForUnprobedStrm`（「未探测的 STRM 文件也跳过探测」，**默认开启**）分成三条路径。

### 2.1 跳过探测 + 不补探测（默认组合）

**触发条件**：`SkipProbeForUnprobedStrm = true` 且 `EnableBackgroundProbeForUnprobedStrm = false`。

**行为**：`allowMediaProbe = false` 直接起播，全程不请求流地址做探测，一次也不请求第二次。

**使用差异**

- 起播最快，源站压力最低 —— 每个条目只产生真实的播放流量。
- **无时长**：进度条无总长度，客户端无法展示码率与轨道列表，字幕/音轨选择可能缺失。
- **进度不会丢**：`PlaybackStateInterceptor` 会接管支持进度续播的条目的进度上报，直接写入客户端上报的位置，绕过 Jellyfin「无时长即视为已看完」的判定，因此不会一开播就被标记成已观看，续播位置也能保存。
- **但也不会自动变成已看完**：完成判定依赖时长，在补探测或预探测写入时长之前，该条目不会被自动标记为已观看。
- 日志会对每个条目记录一条 Warning，说明时长/轨道信息缺失，便于排查。

**适用场景**：冷启动阶段的大库、尚未探测的存量媒体；远程源慢、限流或易超时（AList / WebDAV / 网盘 / 302 直链）；只求「点了能播」，不关心进度与轨道的场景。

### 2.2 跳过探测 + 后台补探测

**触发条件**：上述开关开启，且起播后策略选择「后台补探测」（`EnableBackgroundProbeForUnprobedStrm = true`）。

**行为**：先以 `allowMediaProbe = false` 秒开，**同时**在起播后延迟 `N` 秒（`BackgroundProbeDelaySeconds`，默认 **5 秒**，范围 0–3600）调度一次后台探测，通过 `RefreshMetadata(EnableRemoteContentProbe = true)` 把时长与流信息写入数据库。探测成功后条目转为「有流」，后续播放走秒开路径且信息完整。

**使用差异**

- 首播仍是秒开，探测与播放并行，不阻塞客户端。
- 补探测有两个触发点，内部会去重：构建媒体源时（`GetPlaybackMediaSources`）与客户端上报进度时（`UpdatePlayState`）；同一条目 **10 分钟内最多触发一次**。
- 失败按 `10s → 30s` 间隔重试，最多尝试 **3 次**；仍失败则放弃，留待下次播放。
- 播放停止时默认取消该条目的补探测（`CancelBackgroundProbeOnPlaybackStop = true`）；若还有其他会话正在播放同一条目，则保留，避免误取消。
- 批量预探测运行期间不叠加单集补探测，避免重复探测同一文件。
- 代价：源站会看到一次额外的探测请求，对并发敏感的源站需谨慎。

**适用场景**：希望「先秒开、后补齐」的常规部署；需要续播与看完判定的库；源站允许低频探测请求。

### 2.3 关闭跳过探测（官方兜底）

**触发条件**：`SkipProbeForUnprobedStrm = false`。

**行为**：不干预 `allowMediaProbe`，沿用调用方参数，交回 Jellyfin 官方探测。首次播放需等待远程 `ffprobe`（数秒至探测超时），探测结果写入数据库，该条目此后转为「有流」。

**使用差异**

- 首次播放慢，但信息一次到位，之后永久走秒开路径。
- 此模式下不调度后台补探测（由官方探测负责），配置页的起播后策略、延迟与停止取消选项会自动置灰。
- 作为兼容性兜底：对探测结果准确性要求高、或客户端无法处理无流信息时使用。

## 两类 `.strm` 对比

| 维度 | 有流 | 无流 · 不补探测 | 无流 · 后台补探测 | 无流 · 官方兜底 |
| :--- | :--- | :--- | :--- | :--- |
| 远程探测 | 从不 | 从不 | 起播后 1 次（可重试） | 播放前（每次未成功） |
| 起播耗时 | 毫秒级 | 毫秒级 | 毫秒级 | 数秒～探测超时 |
| 时长 / 进度条 | 完整 | 缺失 | 起播时缺失，补探测后完整 | 首次播放后完整 |
| 续播位置 | 正常 | 保留（无总长） | 保留，补齐后正常 | 正常 |
| 看完判定 | 正常 | 不误标，但也不自动标记 | 补齐后正常 | 正常 |
| 字幕 / 音轨切换 | 正常 | 可能缺失 | 补齐后正常 | 正常 |
| 源站额外请求 | 无 | 无 | 每条目 1 次 | 每次探测失败则重复 |
| 依赖配置项 | 无 | 跳过探测开 + 不补探测 | 跳过探测开 + 后台补探测 | 跳过探测关 |

## 如何选择

**结论先行**：默认组合（跳过探测开 + 不补探测）适合绝大多数部署；只有在你依赖进度条、续播或轨道切换时，才需要开启后台补探测或直接跑预探测。

按目标选择：

| 你的优先级 | 推荐做法 |
| :--- | :--- |
| 极致秒开，源站零额外压力 | 跳过探测 **开** + 不补探测（默认） |
| 秒开 + 进度/续播/轨道切换都要 | 跳过探测 **开** + 后台补探测（延迟 5–15 秒） |
| 媒体信息必须一次准确，容忍首播等待 | 跳过探测 **关**（官方兜底） |
| 库规模大、长期稳定 | 开启**入库自动探测** + 跑一次**增量预探测**，让存量无流条目批量转有流 |
| 源端内容有变动 | 跑一次**全量探测**刷新有流条目的缓存信息 |

**推荐落地顺序**

1. 安装后先看控制台的「缺少流信息」数量；
2. 跑一次**增量探测**（只处理无流条目），等待完成；
3. 勾选**入库自动探测**并保存，保证新增条目自动补齐；
4. 起播后策略保持「不补探测」—— 此时绝大多数条目已是「有流」，无需再补；仅当仍有大量无流条目且不便批量探测时，改选「后台补探测」作为过渡。

## 让无流变成有流

| 方式 | 触发时机 | 范围 | 说明 |
| :--- | :--- | :--- | :--- |
| 增量探测 | 手动启动 | 仅无流条目 | 推荐首选，代价最小 |
| 全量探测 | 手动启动 | 全部 `.strm` | 强制刷新已有信息，可纠正源端变更 |
| 入库自动探测 | 媒体库新增条目 | 单条目 | 监听 `ItemAdded`，后台自动补齐 |
| 起播后补探测 | 无流条目开始播放 | 单条目 | 需开启后台补探测，默认关闭 |

前三种由 `ProbeService` 串行执行并对外暴露进度；同一时刻只允许一个批量任务运行。
